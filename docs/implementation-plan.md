# GMO外貨 スワップポイントカレンダー Androidアプリ実装計画

## 1. 目的

GMO外貨が公開しているスワップカレンダーから、通貨ペアごとの取引日、SP日数、買いスワップ、売りスワップを低頻度で取得・保存し、月間カレンダーとして閲覧できるAndroidネイティブアプリを構築する。

Android専用としてKotlinとJetpack Composeを採用する。公式データの取得・蓄積はバックエンドへ集約し、Androidアプリは読み取りAPIと端末内DBを通じて表示する。取得済みの月はオフラインでも閲覧できる構成とする。

本計画の対象は、データ取得、永続化、表示、定期更新、障害検知までとする。FXの注文、口座情報との連携、投資判断や将来収益の推奨は対象外とする。

## 2. 調査済みの前提

- 取得元はGMO外貨の公開ページとする。
  - `https://www.gaikaex.com/gaikaex/mark/swap/calendar.php`
- ログインせずに閲覧できる。
- `date=YYYYMM` で対象月、`pair=<ID>` で選択通貨ペアを指定できる。
- 1回のHTMLレスポンスには、PC表示用として全通貨ペアのデータが含まれているため、原則として1か月あたり1リクエストで取得する。
- 画面上の掲載項目は、取引日、SP日数、買いスワップ、売りスワップである。
- 将来日ではSP日数のみ掲載され、買い・売りスワップが空欄の場合がある。
- スワップ値 `0` と未発表の空欄は意味が異なるため、データ上も区別する。
- 指定可能な過去月は現状の実測で2014年12月以降だが、公式に保存期間が保証されているわけではない。
- 公開された公式APIは確認できていないため、HTML構造に依存した取得になる。
- AndroidネイティブのHTTP通信にはブラウザのCORS制約は適用されない。ただし、端末数に比例する公式ページへのアクセスと、HTML構造変更のたびにアプリ更新が必要になることを避けるため、公式ページはサーバー側で取得する。
- 公開前・商用利用前に、自動取得、保存、再表示、出典表記の可否をGMO外貨へ確認する。

取得元のHTML構造と過去月の範囲は既存調査の前提を引き継ぐ。実装時に再確認し、取得可能範囲を設定値として管理する。

## 4. 推奨技術構成

初期実装では以下を採用する。AndroidとバックエンドをKotlinで統一し、各責務を分離する。Webフロントエンド、WebViewによる画面実装、PWAは今回の対象に含めない。

| 領域 | 採用技術 | 用途 |
| --- | --- | --- |
| Androidアプリ | Kotlin / Jetpack Compose / Material 3 | ネイティブ画面とテーマ |
| 状態管理 | ViewModel / Coroutines / StateFlow | 非同期処理と画面状態 |
| 端末内DB | Room（SQLite） | 月別データの保存とオフライン閲覧 |
| 設定保存 | Preferences DataStore | 選択通貨ペアなどのユーザー設定 |
| AndroidのHTTP通信 | Ktor Client（OkHttpエンジン） | バックエンドAPIへのHTTPS通信 |
| JSON | kotlinx.serialization | APIリクエスト・レスポンスの変換 |
| Androidの依存性注入 | Hilt | Repository、ViewModel、Workerの依存管理 |
| 端末の定期同期 | WorkManager | 制約付きのバックグラウンドAPI同期 |
| バックエンドAPI | Kotlin / Ktor Server | 読み取りAPIと管理用更新API |
| HTML解析 | jsoup | サーバー側での取得ページ解析 |
| サーバーDB | PostgreSQL | 正規データと取得履歴の保存 |
| SQL・マイグレーション | Exposed SQL DSL / Flyway | DBアクセスとバージョン付きSQL適用 |
| 入力検証 | Kotlinの検証関数・型 | APIクエリとパース結果の検証 |
| 単体・結合テスト | JUnit / kotlinx-coroutines-test / Ktor testApplication / Testcontainers | パーサー、ViewModel、API、PostgreSQLの検証 |
| Android端末テスト | AndroidX Test / Compose UI Test / Room・WorkManagerのテスト支援 | 画面操作、保存、同期の検証 |
| ビルド・静的検査 | Gradle Kotlin DSL / Version Catalog / Android Lint / ktlint | ビルドと依存関係・コード品質管理 |
| 公式ページの定期取得 | デプロイ先のCron | サーバー側の時刻指定取得 |

Android Studioで開発し、最小対応OSはAndroid 8.0（API 26）を初期方針とする。`compileSdk`、`targetSdk`、JDK、Android Gradle Plugin、各ライブラリのバージョンはPhase 1で互換性のある安定版に固定し、配布時点のGoogle Play要件も確認する。

ローカル開発ではDocker ComposeでPostgreSQLを起動し、Ktor Serverを実行する。Androidエミュレーターからは開発マシンのAPIへ接続し、実機では接続可能な開発用URLを使用する。HTTP接続が必要な場合の許可はdebugビルドに限定する。Cron部分はHTTPエンドポイントとCLIの両方から同じユースケースを呼び出せるようにする。

### 4.1 技術選定の根拠

- Android専用のためKotlinとComposeを採用する。Repository、ViewModel、StateFlowによる責務分離は[Android公式のアーキテクチャ推奨事項](https://developer.android.com/topic/architecture/recommendations)を参考にする。
- 表示データはRoomを経由させ、API障害時も保存済みデータを読めるようにする。[オフライン対応の設計](https://developer.android.com/topic/architecture/data-layer/offline-first)と[Room公式ガイド](https://developer.android.com/training/data-storage/room)を参照する。
- サーバーは[Ktor](https://ktor.io/docs/server-create-restful-apis.html)、HTML解析は[jsoup](https://jsoup.org/)、SQLアクセスは[Exposed](https://www.jetbrains.com/help/exposed/about.html)を採用し、Kotlin/JVM上で取得からAPI提供まで実装する。

### 4.2 初期モジュール構成

```text
:app          Androidアプリ（ui / data / syncをパッケージで分離）
:api-contract Kotlin/JVMのAPI DTO（Androidとサーバーで共有）
:server       Ktor API、取得・解析、PostgreSQL保存、管理CLI
```

DTOだけを共有し、Room Entity、サーバーDBモデル、HTMLパーサーは共有モジュールに含めない。金額はAPI上では文字列とし、必要な層で`BigDecimal`へ変換する。機能が増えるまではAndroid側を細かいGradleモジュールに分割しない。

## 5. システム構成

```text
GMO外貨 公開カレンダー
          |
          | 低頻度のHTTP GET
          v
Fetcher -> Parser -> Validator -> Import service
   ^                                  |
   |                                  v
Cron / 管理CLI                    PostgreSQL
                                      |
                                      v
                                  Read API
                                      |
                                      v
WorkManager / 画面操作 -> Android Repository <-> Room
                                      |
                                      | Room由来のFlow
                                      v
                              ViewModel / StateFlow
                                      |
                                      v
                                  Compose UI
```

重要な境界は次のとおりとする。

- FetcherはHTTP取得だけを担当する。
- ParserはHTMLをアプリ内の中間形式へ変換する。
- Validatorは対象月、日数、通貨ペア、値の形式を検証する。
- Import serviceは検証済みデータだけをトランザクションで保存する。
- AndroidのRepositoryはRead APIの検証済みレスポンスをRoomへ保存する。
- UIはViewModelを通じてRoom由来のFlowを購読する。APIやDAOを直接呼び出さない。
- WorkManagerと画面からの手動同期は同じRepositoryを使用する。
- サーバーCronが公式データを更新し、端末同期は保存済みのAPIデータを取得する。端末の操作から公式ページの取得を起動しない。

## 6. データモデル

### 6.1 `currency_pairs`

| カラム | 型 | 内容 |
| --- | --- | --- |
| `id` | UUIDまたはserial | 内部ID |
| `source_pair_id` | integer, unique | GMO外貨ページ上のID |
| `symbol` | varchar, unique | `USD/JPY` など |
| `display_order` | integer | 表示順 |
| `is_active` | boolean | 現在の掲載対象か |
| `first_seen_at` | timestamp | 初回検出日時 |
| `last_seen_at` | timestamp | 最終検出日時 |

通貨ペアは固定配列だけに依存せず、HTMLから検出した一覧と既知の一覧を照合する。未知のIDや名称変更を検出した場合は、取得処理を即座に全失敗させるのではなく、警告として記録し、既知データへの影響を防ぐ。

### 6.2 `swap_points`

| カラム | 型 | 内容 |
| --- | --- | --- |
| `id` | UUIDまたはserial | 内部ID |
| `currency_pair_id` | foreign key | 通貨ペア |
| `trade_date` | date | 取引日 |
| `sp_days` | integer | SP日数 |
| `buy_swap` | decimal(12, 1), nullable | 買いスワップ。空欄はnull |
| `sell_swap` | decimal(12, 1), nullable | 売りスワップ。空欄はnull |
| `publication_state` | enum | `published` / `unpublished` |
| `source_month` | char(6) | 取得に使用した年月 |
| `first_fetched_at` | timestamp | 初回取得日時 |
| `last_fetched_at` | timestamp | 最終確認日時 |
| `updated_at` | timestamp | 値の最終変更日時 |

`currency_pair_id + trade_date` に一意制約を設定する。金額は浮動小数点型ではなくdecimalで保持する。

### 6.3 `fetch_runs`

| カラム | 型 | 内容 |
| --- | --- | --- |
| `id` | UUID | 取得実行ID |
| `source_month` | char(6) | 対象年月 |
| `started_at` | timestamp | 開始日時 |
| `finished_at` | timestamp, nullable | 終了日時 |
| `status` | enum | `running` / `succeeded` / `failed` / `rejected` |
| `http_status` | integer, nullable | 取得元のHTTPステータス |
| `record_count` | integer | 検証済みレコード数 |
| `content_hash` | varchar, nullable | HTMLの変更検知用ハッシュ |
| `error_code` | varchar, nullable | 機械判定用エラーコード |
| `error_message` | text, nullable | 調査用メッセージ |

HTML全体は原則として永続保存せず、ハッシュと解析結果を保存する。テスト用fixtureは必要最小限に加工し、リポジトリへ格納する。

### 6.4 Android端末内データ

上記6.1〜6.3はサーバー側のモデルとする。端末にはRoomで次を保存する。

- `cached_currency_pairs`：APIの通貨ペアID、シンボル、表示順、有効状態。
- `cached_swap_points`：通貨ペアIDと取引日を複合主キーとし、SP日数、買い・売り金額、公開状態を保存する。金額はnullableな10進文字列として保存し、`Double`を経由しない。
- `cached_months`：対象月、公式データの最終取得日時`source_fetched_at`、端末の最終同期成功日時`last_synced_at`、月全体の同期完了状態。

MVPでは対象月の全通貨ペアを同期し、選択ペアの絞り込みは端末内で行う。APIの年月・全件の形式を検証してから、月データと同期メタデータを同一トランザクションで置換する。途中失敗や不正レスポンスでは既存データを維持する。

取引日は`LocalDate`、年月は`YearMonth`として扱い、取引日をタイムゾーン変換しない。「今月」と公式取得日時の表示はAsia/Tokyoを基準とする。時刻はAPIのオフセット付き日時を`Instant`へ変換して扱う。

選択通貨ペアはDataStore、表示月はViewModelの`SavedStateHandle`で保持する。Roomのスキーマをエクスポートし、更新時にはマイグレーションを用意する。

## 7. 取得・解析仕様

### 7.1 取得

1. 対象月を `YYYYMM` として検証する。
2. 公式ページへタイムアウト付きでGETする。
3. 429、5xx、タイムアウトは指数バックオフ付きで最大3回再試行する。
4. 200以外のレスポンスは保存処理へ渡さない。
5. User-Agentにはアプリ名と連絡先を設定できるようにする。
6. 同じ対象月の同時実行をロックする。

通常更新は当月と前月を対象とし、翌月の掲載確認だけを追加で許可する。過去データの初期投入は、1リクエストごとに間隔を設けた専用コマンドで実施する。

### 7.2 HTML解析

- ページ見出しに表示された年月を読み、要求した年月と一致することを確認する。
- 通貨ペアIDとシンボルは選択肢およびテーブル見出しから取得する。
- PC用の `swaplist` テーブルを解析し、全通貨ペアを1回で取得する。
- 各行の日付に要求年月の年を補ってISO日付へ変換する。
- SP日数を整数へ変換する。
- 買い・売りスワップはdecimalへ変換し、空文字はnullとする。
- 表示用の曜日は保存せず、画面側で日付から算出する。
- CSSクラス名だけでなく、見出しと列の対応も確認し、列ずれを検知する。

### 7.3 保存前検証

最低限、次をすべて通過した場合だけ保存する。

- ページ上の年月が要求年月と一致している。
- 対象月の日数と行の日付範囲が一致している。
- 同一通貨ペア・同一日が重複していない。
- SP日数が0以上の妥当な整数である。
- 金額が空欄または妥当な数値である。
- 通貨ペア数が急に0件または大幅減少していない。
- 全体のレコード数が期待範囲内にある。

検証失敗時は既存データを変更せず、`fetch_runs.status = rejected` として記録する。取得元が不正な年月を当月へフォールバックする挙動があるため、HTTP 200だけで成功と判定してはならない。

### 7.4 更新ルール

- 新規行は挿入する。
- 既存行に変更があれば更新する。
- 数値 `0` は通常値として保存する。
- 空欄はnullとして保存する。
- 一時的な解析不良で、公開済み数値を一括してnullへ上書きしない。
- 公開済み値が変更された場合は公式側の訂正として更新し、`updated_at` を変更する。
- 変更件数が異常に多い場合は保存を保留し、警告する。

## 8. API設計

### 8.1 カレンダーデータ

```http
GET /api/swap-points?month=2026-09&pairs=USD%2FJPY,MXN%2FJPY
```

レスポンス例：

```json
{
  "month": "2026-09",
  "source": {
    "name": "GMO外貨",
    "url": "https://www.gaikaex.com/gaikaex/mark/swap/calendar.php",
    "lastFetchedAt": "2026-09-19T07:15:00+09:00"
  },
  "pairs": [
    {
      "id": "ad31915d-38b3-4f68-9b20-d91d85d7e3ee",
      "symbol": "USD/JPY",
      "points": [
        {
          "tradeDate": "2026-09-01",
          "spDays": 1,
          "buySwap": "120.0",
          "sellSwap": "-120.0",
          "publicationState": "published"
        }
      ]
    }
  ]
}
```

金額はJSONの浮動小数点誤差を避けるため文字列で返し、未発表はJSONの`null`とする。`pairs`省略時は全通貨ペアを返し、Androidの月単位同期では省略する。

未取得月を空の正常レスポンスと混同しないよう、月全体を取得済みの場合だけ200を返す。不正な年月・ペアは400、取得可能範囲外は404（`MONTH_OUT_OF_RANGE`）、範囲内で未取得の月は404（`MONTH_NOT_AVAILABLE`）として機械判定用コードを返す。GETによる公式ページへのオンデマンド取得は行わない。

### 8.2 通貨ペア一覧

```http
GET /api/currency-pairs
```

有効な通貨ペアの内部ID、シンボル、表示順を返す。過去月のレスポンスには、その月に存在する廃止済みペアの識別情報も含める。月データにも内部IDを含め、Roomの保存キーとする。APIのIDは文字列に統一する。

### 8.3 取得範囲

```http
GET /api/availability
```

取得元の対応範囲と、サーバーで取得済みの年月一覧を別フィールドで返す。Androidはこれを使って前月・翌月操作の境界と、未取得月の案内を表示する。

### 8.4 更新エンドポイント

```http
POST /api/internal/fetch
```

- Cron専用とし、署名または秘密トークンで保護する。
- 任意URLを受け取らず、サーバー側で許可した取得元だけを使用する。
- 同じサービス層をCLIからも呼べるようにする。
- Androidアプリからは呼び出さず、管理トークンをAPKへ含めない。

## 9. 画面設計

### 9.1 メイン画面

- 上部に年月、前月、次月、今月へ戻る操作を置く。
- 通貨ペアを検索・選択できるようにする。
- Composeで月間カレンダーと選択日の詳細を表示する。カレンダーセルは日付・SP日数・公開状況を中心とし、買い・売りの金額は日付選択後の詳細へ表示する。
- 複数ペア選択時は日付ごとの詳細に通貨ペア別カードを並べる。SP日数がペアごとに異なる場合はセルで共通値として扱わず、カードごとに表示する。
- 縦向きスマートフォンを基本とし、横向き・タブレットの広い画面ではカレンダーと詳細を左右に配置する。
- Material 3のテーマ、ダークモード、edge-to-edgeのインセットに対応する。
- 買いと売りを色だけに依存せず、符号とラベルで区別する。
- SP日数が複数の日を視覚的に識別できるようにする。
- 未発表値は `—` と「未発表」の補助文言で表示する。
- 0円は `0.0` と表示し、未発表と混同させない。
- 最終取得日時、出典、予定額は変更される可能性がある旨を表示する。
- 手動更新操作を設け、APIから端末内データを同期する。公式ページの再取得とは区別する。
- 出典リンクは外部ブラウザで開く。

### 9.2 状態表示

- 初回読み込み中
- データなし
- APIエラー
- オフライン（保存済みデータあり／なし）
- 古いキャッシュを表示中
- サーバーで未取得の月
- 対象月が取得可能範囲外

API障害時でも保存済みデータがあれば表示し、更新日時と警告を併記する。

画面回転やバックグラウンド復帰で選択月・通貨ペアを保持する。TalkBackの読み上げ、文字拡大、タップ領域を確認し、状態は色だけで伝えない。

## 10. 定期更新と初期投入

### 10.1 サーバー側の通常更新

- Asia/Tokyoを基準に毎日7時15分頃に当月を取得する。
- 反映遅延を考慮し、8時台にも再取得できる設定とする。
- 月初は前月も再取得し、月末付近の訂正を反映する。
- 翌月は公開状況を低頻度で確認し、要求年月と一致したレスポンスだけを取り込む。未掲載の場合はアプリへ未取得状態を返す。
- 土日を含めて実行してもよいが、HTMLハッシュが同じ場合はスワップ値の更新を省略し、取得成功履歴と最終確認日時は更新する。
- 失敗時は既存キャッシュを継続提供する。

### 10.2 Android側の同期

- 起動時・表示月変更時にRoomを先に表示し、未保存または前回同期から1時間以上経過していればRead APIへ同期する。手動更新では経過時間にかかわらず同期できる。
- WorkManagerのunique periodic workをネットワーク接続条件付きで登録し、約12時間ごとに当月と前月を同期する。選択中の過去月は画面表示時に同期する。
- WorkManagerは省電力制御などで遅延するため、7時15分などの正確な時刻を保証する用途には使わない。時刻指定の公式ページ取得はサーバーCronが担う。
- 同一月の並行同期を抑止し、通信タイムアウト・429・5xxは上限付きバックオフで再試行する。4xxの入力不備や未取得月は自動再試行を繰り返さない。
- 端末同期の成功時刻で公式データの取得時刻を上書きしない。当月の公式取得が24時間以上成功していない場合は古いデータとして案内する。
- バックグラウンド同期が実行されなくても、次回起動時と手動更新で追いつけるようにする。

定期処理の制約は[WorkManagerのWorkRequest定義ガイド](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)を参照する。

### 10.3 初期投入

- 実装予定の管理CLI例：`./gradlew :server:run --args="fetch-history --from 2024-01 --to 2026-09"`
- 新しい月から古い月へ、または月単位の直列処理とする。
- リクエスト間隔、最大件数、再開位置を設定可能にする。
- 最初は直近12か月だけ投入し、必要性を確認後に範囲を広げる。
- 2014年12月より前を要求しない。

## 11. テスト計画

### 11.1 パーサー単体テスト

- 初回投入
- 同一データの再投入が冪等であること
- 公式側の訂正による更新
- nullと0の区別

- 不正パラメータへの400応答
- 未取得月・範囲外月の404とエラーコード、取得範囲APIとの整合性

- API文字列金額と`BigDecimal`の変換、nullと0の保存・再読込

- WorkManagerの制約と再試行、定期処理の重複登録防止

## 12. 監視・運用

- 取得成功率、最終成功時刻、取得件数、変更件数を記録する。
- 24時間以上更新成功がない場合に通知する。
- 通貨ペア数、行数、HTMLハッシュの急変を通知する。
- ログにレスポンス本文全体や秘密トークンを出力しない。
- 取得元へのリクエスト数をメトリクス化する。
- 画面の最終取得時刻は、表示対象月についてサーバーDBに記録された公式データの最終成功取得時刻を使用する。HTMLハッシュが同一でも成功確認時刻は更新する。
- 端末の同期失敗は画面で案内し、サーバー側の取得失敗とは区別する。

## 13. セキュリティとコンプライアンス

- 取得先ホストを固定し、SSRFを防止する。
- 取得処理、API、Cronにタイムアウトとレート制限を設ける。
- 内部更新APIを認証する。
- DB接続情報とCronトークンは環境変数で管理する。
- AndroidのreleaseビルドはHTTPSを使用し、平文HTTPを禁止する。
- APKへDB接続情報、管理APIの秘密情報、署名鍵を含めない。署名鍵・パスワードはリポジトリ外で管理する。
- MVPの端末権限は通信に必要な`INTERNET`・`ACCESS_NETWORK_STATE`を基本とし、通知やストレージの実行時権限は必要な機能を追加する時点で検討する。
- 出典名、公式ページへのリンク、取得日時、予定値に関する注意書きを表示する。
- GMO外貨のロゴや画像は無断で複製せず、原則としてテキスト表記にする。
- 一般公開または収益化の前に、データ再表示の可否と必要な表記をGMO外貨へ問い合わせる。
- 利用条件に反することが判明した場合、定期取得を停止できる設定を用意する。

## 14. 実装フェーズ

### Phase 0: 利用条件と要件の確定

- 公開範囲を個人利用、限定公開、一般公開から決定する。
- 対象期間と初期表示通貨ペアを決定する。
- GMO外貨への確認が必要な場合は問い合わせる。
- デプロイ先とPostgreSQL提供先を決定する。
- AndroidのアプリID、最小対応OSの方針、APK配布またはGoogle Play公開の経路を決定する。

完了条件：公開範囲、対象データ、運用責任が文書化されている。

### Phase 1: プロジェクト基盤

- Gradleの`:app`、`:api-contract`、`:server`を作成し、SDK・JDK・依存バージョンを固定する。
- Kotlin、Compose、Material 3、Hilt、Room、DataStore、Ktor Clientを導入する。
- Ktor Server、PostgreSQL、Exposed、Flywayとサーバー環境変数の検証を設定する。
- debug/releaseのAPI接続先を分ける。
- CIでビルド、Lint、JVMテスト、エミュレーターテストを実行できるようにする。

完了条件：Androidアプリがエミュレーターで起動し、サーバーとともにローカル・CIで正常にビルドできる。

### Phase 2: 取得・解析

- Fetcher、Parser、Validatorを実装する。
- fixtureとパーサー単体テストを追加する。
- 手動CLIで1か月分をJSON出力できるようにする。
- 異常レスポンスの拒否を確認する。

完了条件：対象月の全通貨ペアを正規化し、テストが通る。

### Phase 3: 保存・API

- DBスキーマとマイグレーションを作成する。
- トランザクション付きupsertを実装する。
- `fetch_runs` を記録する。
- 読み取りAPIと内部更新APIを実装する。
- 共有DTO、取得範囲API、Android向けのエラー契約を実装する。

完了条件：再実行可能な取得処理と月単位のAPIが動作する。

### Phase 4: Androidの保存・同期

- Room Entity・DAO、APIクライアント、Repositoryを実装する。
- 月単位同期、DataStoreによる設定保存、WorkManagerによる定期同期を実装する。
- API障害・オフライン・途中失敗でも既存データが残ることを確認する。

完了条件：取得済みの月をオフラインで読み出せ、再同期による訂正が原子的に反映される。

### Phase 5: AndroidカレンダーUI

- ViewModelとStateFlowによる画面状態を実装する。
- Composeで月間カレンダー、日付詳細、月移動、通貨ペア選択、手動更新を実装する。
- ローディング、エラー、データなし、古いキャッシュ状態を実装する。
- 出典、最終取得日時、注意書きを追加する。
- 画面回転・プロセス再生成からの復元、ダークモード、アクセシビリティを確認する。

完了条件：Android端末で主要操作ができ、nullと0を判別でき、オフライン状態を確認できる。

### Phase 6: 自動更新・運用・Android配布

- Cronと認証を設定する。
- 初期データ投入を実施する。
- 失敗通知と構造変更検知を設定する。
- 本番環境で低頻度の取得を確認する。
- 実機でAPI接続、オフライン表示、バックグラウンド復帰を確認する。
- アプリ名・アイコン・バージョンと署名設定を整え、署名付きAPK（直接配布）またはAAB（Google Play）を生成する。
- Google Playを利用する場合は、公開時点の対象API・データセーフティ等の要件を確認し、内部テストを経て配布する。

完了条件：サーバー定期更新と端末同期が動作し、障害時も保存済みデータを表示でき、選択した配布経路でインストール・更新を確認できる。

## 15. MVP受け入れ条件

- 指定月の通貨ペア別スワップポイントが表示される。
- 前月・翌月へ移動できる。
- SP日数、買い、売りが公式ページと一致する。
- 数値0と未発表が異なる表示になる。
- 取得元の一時障害で保存済みデータが消えない。
- 要求月と異なるHTMLが返された場合、取り込みを拒否する。
- 取得処理が同じ月に再実行されても重複行ができない。
- 画面に出典と最終更新日時が表示される。
- 主要なパーサー、API、画面操作のテストがCIで成功する。
- 取得頻度が設定値を超えない。
- Android実機とエミュレーターで起動し、署名付き配布ビルドがインストールできる。
- オフラインでも同期済みの月を閲覧でき、未同期の月は理由とともに案内される。
- 画面回転・プロセス再生成後に表示月と選択ペアが復元される。
- WorkManagerの実行が遅延しても、起動時・手動更新で同期できる。
- 端末の更新操作では公式ページの取得が発生せず、公式取得日時と端末同期日時が区別される。
- Androidリリース成果物に管理トークンやDB接続情報が含まれない。

## 16. 主なリスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| HTML構造変更 | 取得停止、誤データ | 厳格な検証、fixture、件数監視、既存値の保護 |
| 公式値の事後訂正 | 表示値の不一致 | 当月・前月の再取得、更新日時の記録 |
| 未発表と0の混同 | 誤表示 | nullable decimalと公開状態を分離 |
| 不正な年月が当月へフォールバック | 別月への誤保存 | ページ見出し年月と要求月を照合 |
| 取得元障害や制限 | 更新停止 | 低頻度取得、再試行、キャッシュ継続表示 |
| 利用条件上の問題 | 公開停止 | 公開前確認、出典表示、停止スイッチ |
| 通貨ペア追加・廃止 | 表示欠落 | 動的検出、active管理、未知ペア通知 |
| Androidの省電力制御 | 端末同期の遅延 | WorkManager、起動時・手動同期、取得日時表示 |
| 端末内DBの移行不備 | 保存済みデータの消失 | Roomスキーマ管理、マイグレーションテスト |
| サーバーとアプリの更新時期の差 | API互換性の破壊 | 共有DTO、後方互換のある追加変更、旧アプリでの検証 |
